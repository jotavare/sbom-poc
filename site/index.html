SBOM Pipeline Map

How one push turns five deliberately vulnerable apps into SBOMs for every stage, checks them, and reports what they show. Each CI job runs the same make pipeline you can run locally.

The four SBOM stages

CISA defines SBOM types by when they're made; each SBOM records its stage in CycloneDX metadata.lifecycles.

One CI job, step by step

The sbom.yml workflow runs this job once per app (python, node, go, java, rust) in parallel, about 6 minutes in total.

fails the build a failed check stops the jobreport results only
  1. 1

    Tests

    make test

    Builds the Dockerfile's test stage, which runs the app's own tests.

    fails the build
  2. 2

    Build the image

    build-image.sh

    BuildKit builds the runtime image, attaches its own SBOM and SLSA provenance, pushes it to a local registry and pulls it back, so every tool scans the same digest.

    stage 2 attestationBuildKitlocal registry
    → artifact.json, buildkit-image.spdx.json, buildkit-provenance.json
  3. 3

    Generate SBOMs

    generate-sbom.sh

    Source scans (stage 1), the native build SBOM (stage 2) and image scans (stage 3). No tool gets the Docker socket: the image is scanned from a saved tarball, every tool call has a 10-minute timeout and its own log.

    SyftTrivycdxgencyclonedx-py · npm · gomod · maven · cargo
    → CycloneDX 1.7, SPDX 2.3, SPDX 3.0.1 files
  4. 4

    Label stages, derive views

    label-lifecycle.sh · make-views.sh

    Every SBOM gets its stage. Each image SBOM is split into an OS view (deb packages) and an app view (language packages), so different policies can apply.

    jq
    → views/<gen>-image-os, -app
  5. 5

    Check

    check-sbom.sh

    Every expected file exists, the image has a digest, every SBOM declares its stage, the vulnerable marker packages are found, and no dev/test dependency ships.

    fails the build
  6. 6

    Runtime SBOM

    runtime-sbom.sh

    Runs the unchanged image with the app under a static strace, sends the probes, and maps every opened or executed file to its package.

    stage 4strace 7.3
    → runtime.cdx.json, ships-vs-runs table
  7. 7

    Blind spots

    unmanaged-files.sh

    Lists executables and libraries in the image that no package claims, so no package-based SBOM describes them.

    report
  8. 8

    Validate

    validate-sbom.sh

    Checks every SBOM against its specification. Known generator bugs are recorded and shown as warnings instead of being hidden.

    fails the buildcyclonedx-clipyspdxtoolsspdx3-validatejsonschema-rs
  9. 9

    Report

    summary.sh

    Compares the generators and their dependency graphs, checks licences against the policy, and scores SBOM quality; writes the app's report by stage.

    reportgrantsbomqs
    → reports/summary.md, CI job summary

Where results go

Per app

Artifact sbom-<app>: all SBOMs, views, reports and tool logs, kept 30 days.

Combined

The report job merges every app's summary into SBOM-REPORT.md (artifact sbom-report), stamped with commit, tool versions and image digests.

By hand

The scancode.yml workflow compares declared licences with those found in the files (python, node, java). Slow, so run when needed.
