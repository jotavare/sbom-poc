SBOM Pipeline Map

How one push turns five deliberately vulnerable apps into SBOMs for every stage, checks them, scans them for vulnerabilities, and reports what they show. Each CI job runs the same make pipeline you can run locally.

One CI job, step by step

The sbom.yml workflow runs this job once per app (python, node, go, java, rust) in parallel.

fails the build a failed check stops the jobreport results only
  1. 1

    Tests

    make test

    Builds the Dockerfile's test stage, which runs the app's own tests.

    fails the build
  2. 2

    Build the image

    build-image.sh

    BuildKit builds the runtime image, attaches its own SBOM and SLSA provenance, pushes it to a local registry and pulls it back, so every tool scans the same digest. artifact.json records the index, manifest and config digests.

    stage 2 attestationBuildKitlocal registry
    → artifact.json, buildkit-image.spdx.json, buildkit-provenance.json
  3. 3

    Generate SBOMs

    generate-sbom.sh

    Source scans (stage 1), the native build SBOM (stage 2) and image scans (stage 3). No tool gets the Docker socket: the image is scanned from a saved tarball, every tool call has a timeout and its own log.

    SyftTrivycdxgencyclonedx-py · npm · gomod · maven · cargo
    → CycloneDX 1.7, SPDX 2.3, SPDX 3.0.1 files
  4. 4

    Label stages, derive views

    label-lifecycle.sh · make-views.sh

    Every SBOM gets its stage. Each image SBOM is split into an OS view (deb packages) and an app view (language packages), so different policies can apply.

    jq
    → views/<gen>-image-os, -app
  5. 5

    Check

    check-sbom.sh

    Every expected file exists, the image has a digest, every SBOM declares its stage, the vulnerable marker packages are found, and no dev/test dependency ships.

    fails the build
  6. 6

    Runtime SBOM

    runtime-sbom.sh

    Runs the unchanged image with the app under a static strace (without the container health check), sends the probes, and maps every opened or executed file to its package. Paths are resolved through the image's symlinks, and script interpreters (#!) count as used. Java also writes one class-load log per JVM; a nested JAR counts only if classes were loaded from it.

    stage 4strace 7.3
    → runtime.cdx.json, ships-vs-runs table
  7. 7

    Blind spots

    unmanaged-files.sh

    Lists code in the image that no package claims (ELF binaries, #! scripts, libraries and other code files), so no package-based SBOM describes it. A file that only has the execute bit, such as a CA bundle, isn't counted.

    report
  8. 8

    Validate

    validate-sbom.sh

    Checks every SBOM against its specification. Known generator bugs are recorded and shown as warnings instead of being hidden.

    fails the buildcyclonedx-clipyspdxtoolsspdx3-validatejsonschema-rs
  9. 9

    Vulnerabilities

    scan-vulns.sh

    Three scanners read the three image SBOMs and the build SBOM, never the image. Findings are mapped to one CVE per package; findings on cdxgen's Debian source packages are moved onto the binary packages built from them, so a flaw is counted once. Severity is the vendor rating from Grype and Trivy (the distribution's or the advisory's), and OSV-Scanner's CVSS only when there is none; fix versions also come from Grype and Trivy first. The merged findings are checked against the planted CVEs and ranked: known exploited (KEV), ran at runtime, severity, EPSS. They become one SARIF file, shown in GitHub code scanning, with accepted findings marked as suppressed.

    GrypeTrivyOSV-ScannerSARIF 2.1.0
    → reports/vulns.md, vulns/vulns.sarif, raw scanner JSON
  10. 10

    Report

    summary.sh

    Compares the generators and their dependency graphs, checks licences against the policy, and scores SBOM quality; writes the app's report by stage. Package counts include runtimes recorded with a purl (such as node) and leave out cdxgen's cryptographic assets. The report also says which image SBOMs record the image's digest.

    reportgrantsbomqs
    → reports/summary.md, CI job summary
  11. 11

    Vulnerability gate

    vuln-gate.sh

    Fails on a critical or high vulnerability with a fix, found by any scanner on any image SBOM, that isn't accepted (each acceptance has a reason and an expiry date), or a planted CVE no scanner found. Runs last, so the report always exists.

    fails the build

Where results go

Per app

Artifact sbom-<app>: all SBOMs, views, reports and tool logs, kept 30 days.

Combined

The report job merges every app's summary into SBOM-REPORT.md (artifact sbom-report), stamped with commit, tool versions and image digests.

Code scanning

Each app's vulns.sarif is uploaded to the repository's Security tab: one alert per package and CVE, pointing at the file that declares the package. Accepted findings are marked as suppressed. GitHub only displays it; the findings and the gate are the pipeline's own.

By hand

The scancode.yml workflow compares declared licences with those found in the files (python, node, java). It runs only when started by hand.
