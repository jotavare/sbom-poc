# SBOM types: what they are, what the standards say, and how this PoC maps to them

An SBOM is not one thing. *When* and *how* it's generated decides what it can see. This page summarises the primary sources (read on 2026-11-17) and maps every SBOM in this repo to them.

## The sources

| Source | What it defines | Status |
|---|---|---|
| **CISA, *Types of Software Bill of Material (SBOM) Documents*** ([CISA](https://www.cisa.gov/resources-tools/resources/types-software-bill-materials-sbom), [OpenSSF copy](https://sbom-catalog.openssf.org/sbom-types)) | Six SBOM types: Design, Source, Build, Analyzed, Deployed, Runtime | Published guidance (2023) |
| **CycloneDX 1.6, `metadata.lifecycles`** ([spec](https://cyclonedx.org/docs/1.6/json/), also ECMA-424) | The field that records the phase(s) in which an SBOM's data was captured | Standard |
| **CISA, *2025 Minimum Elements for an SBOM*** ([PDF](https://www.cisa.gov/sites/default/files/2025-08/2025_CISA_SBOM_Minimum_Elements.pdf)) | Adds **Generation Context** as a new *minimum* element, plus Component Hash, License, Tool Name | Public comment draft, Aug 2025 |
| **BSI TR-03183-2 v2.1.0** (German Federal Office for Information Security), Part 2: SBOM | Requirements an SBOM must meet; used as the technical basis for the EU Cyber Resilience Act (CRA) | v2.1.0, 2025-08-20 |

## The SBOM types (CISA), with the matching CycloneDX phase

| CISA type | CISA definition (short quotes) | CycloneDX `lifecycles.phase` | CycloneDX wording (short quotes) |
|---|---|---|---|
| **Design** | "SBOM of intended design of included components (some of which may not exist)" | `design` | "BOM produced early in the development lifecycle" |
| **Source** | "created directly from the development environment, source files, and included dependencies" | `pre-build` | "information obtained prior to a build process" |
| **Build** | "generated as part of the process of building the software to create a releasable artifact" | `build` | "information obtained during a build process"; precise resolved versions and provenance usually available |
| **Analyzed** | "generated through analysis of artifacts … after its build"; also called a "3rd party" SBOM | `post-build` | "information obtained after a build process has completed" |
| **Deployed** | "an inventory of software that is present on a system" | `operations` | "inventory that is running and operational" |
| **Runtime** | generated by instrumenting the running system: components present, external call-outs, dynamically loaded components; also "Instrumented" or "Dynamic" SBOM | `operations` | (same) |

CycloneDX also has `discovery` (network discovery) and `decommission` (retired inventory), which don't apply here.

### Strengths and limits (CISA, paraphrased)

| Type | Strengths | Limits |
|---|---|---|
| Source | Visibility without the build; shows the dependency tree; fix at the source | Can list components that never run or are compiled out; may miss runtime/plugin/platform components |
| Build | **More confidence it's correct** (information available during the build); sees more than source; **the same workflow can sign the SBOM and the artifact** | Needs changes to the build; depends on the build environment; may miss indirect/runtime dependencies and dynamically linked versions |
| Analyzed | Needs no build access; **verifies SBOMs from other sources; can find hidden dependencies** others miss | **Omissions, errors, approximations** when components can't be recognised; heuristics |
| Runtime | Shows **what is actually in use**, incl. dynamically loaded components and external connections | Needs the system running (overhead); some parts only appear once fully exercised |

CISA states that one SBOM document may combine information from several types, and that the types complement each other.

## What the newest requirements say

**CISA 2025 (draft), Generation Context** is a new minimum element:
> "The relative software lifecycle phase and data available at the time the Software Producer generated the SBOM (before build, during build, after build)."

It explains: pre-build/source SBOMs come from repositories; a build SBOM is generated "as part of the creation of a releasable artifact … recording the exact components that contributed to the artifact"; "Binary analysis tools can generate an analyzed or post-build SBOM."

**BSI TR-03183-2 v2.1.0** (section 5.1):
> "An SBOM compliant with this Technical Guideline MUST contain the same information as available during the build process"

and, for its appendix definition of a Build SBOM (8.4.3): "created as part of the build process based on e.g. source files, dependency information, already created components, volatile build process data and other SBOMs". It also requires:
- **Formats:** CycloneDX **1.6 or higher**, or SPDX **3.0.1 or higher** (section 4).
- **Depth:** recursive dependency resolution for everything in the scope of delivery (section 5.1).
- **Hash:** SHA-512 of each deployable component (section 5.2).
- **Licences:** distinguishes original, concluded and effective licences.

### Where the industry is heading

1. **Producers are expected to generate SBOMs during the build** (BSI: MUST contain build information; CISA: build SBOMs record "the exact components that contributed to the artifact").
2. **Every SBOM must say when it was made** (CISA Generation Context; CycloneDX `lifecycles`).
3. **Analyzed (post-build) SBOMs verify** build SBOMs and catch what the build didn't install (base images, bundled binaries). They're the consumer's tool and the producer's cross-check.
4. **Runtime SBOMs** are the newest type: they separate what ships from what's actually used.
5. **Signed, attached to the artifact** (CISA Build strengths; BuildKit/in-toto attestations).

## How this PoC maps to it

| File | CISA type | CycloneDX phase | Made by | Answers |
|---|---|---|---|---|
| `syft/trivy/cdxgen-source.*` | Source | `pre-build` | Scanners on the app directory | What did we declare (incl. dev deps)? |
| `native-build.cdx.json` | **Build** | `build` | The language's package manager plugin, inside the Docker build | What did the build resolve and install for the app? (correct dependency tree) |
| `buildkit-image.spdx.json` (+ provenance) | Build (attestation) | `build` | BuildKit, during the build; scans the image it just built; attached to the image digest | What's in the artifact, as recorded by the builder that produced it? |
| `syft/trivy/cdxgen-image.*` | **Analyzed** | `post-build` | Scanners on the finished image | What's physically in the image, wherever it came from? (finds base-image content like `npm`) |
| `views/*-image-{os,app}` | (views of Analyzed) | `post-build` | Filters | Same, split by owner / policy |
| *runtime SBOM (planned)* | **Runtime** | `operations` | Run + exercise the container, record files used | What actually runs? |

### Example: why Build and Analyzed differ (Node app)

- **Build** SBOM (`cyclonedx-npm`): **65** npm packages, exactly what npm installed for the app, with the correct tree (4/4 direct dependencies linked).
- **Analyzed** SBOM (Syft on the image): **214** npm packages, because the `node:24-slim` base image already contains **npm itself** (145 packages). The build never installed npm, so the build SBOM can't see it; scanning the artifact does.
- **Runtime** SBOM (planned) is expected to show npm is never loaded: the gap between "ships" and "runs" is removable attack surface.
